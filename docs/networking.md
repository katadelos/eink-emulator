# Networking and SSH

All 26 catalogue models have carried Wi-Fi and USB Ethernet traffic concurrently
in stock guests. Every row below includes association, DHCP and gateway packet
checks on Wi-Fi, and a separate USB gateway check. USB starts automatically in
newly prepared images. Wi-Fi uses the stock radio driver and supplicant to join
the emulated open `Kindle-QEMU` access point.

## Addresses and services

| Transport | Guest address | Gateway | DNS |
| --- | --- | --- | --- |
| Wi-Fi | DHCP, normally `10.0.2.15/24` | `10.0.2.2` | `10.0.2.3` |
| USB | `192.168.15.244/24` | `192.168.15.201` | `192.168.15.3` |

The launcher supplies independent QEMU user-network backends for both interfaces.
Wi-Fi is normally `wlan0`; Forma's stock Realtek driver calls it `eth0`.
USB is `usb0`. Kindle preparation keeps the stock radio jobs, reserves the gadget
controller for networking, and installs USB routing with metric 2048. Native
Wi-Fi events and DHCP completion restore that route and USB DNS after the stock
network manager rewrites them. Kindle 4 uses an init-supervised event listener;
later Kindles use Upstart. No periodic network polling daemon is installed.

## Kindle SSH

Newly created Kindle images include Dropbear 2026.94 and start it automatically:
Kindle 4 uses a respawning init entry; Touch and later use the Upstart `sshd`
job. The server listens on guest port 22 on both USB and Wi-Fi, including when
Wi-Fi connects after boot. The prepared firewall permits SSH on both interfaces.
Scribe 1 and 2 use SSH too. Kobos retain USB telnet on host port 2323, configurable
with `--telnet-port`.

The first Kindle image build generates one Ed25519 login key at
`build/ssh/id_ed25519`, reused for every Kindle. Only its public key is installed
in the guest, at `/etc/eink-ssh/authorized_keys`. These binaries accept public
keys only; there is no SSH password. Keep the private key when cleaning build
outputs if you want to retain access to existing devices.

```sh
# USB (available automatically after boot)
ssh -i build/ssh/id_ed25519 -p 2222 root@127.0.0.1

# Wi-Fi (after joining Kindle-QEMU)
ssh -i build/ssh/id_ed25519 -p 2223 root@127.0.0.1

# Choose different host ports for another running device
./eink run my-reader --ssh-port 4022 --wifi-ssh-port 4023
ssh -i build/ssh/id_ed25519 -p 4022 root@127.0.0.1

# File transfer uses the SCP protocol; these builds do not include SFTP.
scp -O -i build/ssh/id_ed25519 -P 2222 book.txt root@127.0.0.1:/mnt/us/
```

All host forwards bind to `127.0.0.1`. Each guest generates its own host key
under `/var/local/eink-ssh` on first boot and retains it across restarts. Different
devices on the same host port have different host identities; use SSH's
`HostKeyAlias` option to keep their known-hosts entries separate.
Server logs are in `/var/log/sshd.log`. On Upstart devices, `initctl status sshd`
and `restart sshd` inspect and restart the service from the serial console.

Create a new machine to obtain these additions; existing saved disks keep
their original guest configuration. Changes to the bundled additions or shared
public key invalidate the base-image cache for future creations. See
[guest additions](../guest-additions/README.md) for ABI selection.

Select `Kindle-QEMU` through the guest Wi-Fi controls. For serial diagnosis,
Amazon's `wpa_cli` wraps the SSID itself:

```sh
wpa_cli -i wlan0 add_network
wpa_cli -i wlan0 set_network 0 ssid Kindle-QEMU
wpa_cli -i wlan0 set_network 0 key_mgmt NONE
wpa_cli -i wlan0 select_network 0
```

Use the network ID returned by `add_network`. Keep the stock `ap_scan=2` on
AR6003 Kindles: forcing `ap_scan=1` exposes a bug in their old stock supplicant.
MediaTek direct-console probes used `ap_scan=1`. Kobo uses standard SSID syntax;
hex `4b696e646c652d51454d55` avoids shell quoting differences. Association through
normal guest controls also starts its normal DHCP handling.

## Implementation and verification

The fixes cover catalogue/launcher wiring, native SDIO/DMA radio transport,
guest radio startup, cable detection and charger notifications, gadget
configuration, ECM/RNDIS negotiation, and route/DNS coexistence. Elipsa's stock
kernel has RNDIS only, so its image uses configfs rather than a missing g_ether
module. Paperwhite 4 also needed formatted keys, varlocal and userstore
partitions for a stable fresh boot. Kobo Mini's firmware IVT boot handling was
repaired, and missing local firmware/source partitions were recovered.

MT8115 Scribes use prepared development copies of the boot FIT and rootfs;
see [Scribe 3](scribe-3.md) and [Scribe Colorsoft](scribe-colorsoft.md). Imported
source firmware and existing persistent machine disks are not rewritten.

Link-loss/reconnect checks passed on AR6003, Broadcom, RTL8192ES, MT8113 and
MT8171.
Direct-console Kindle profiles were reconnected with `wpa_cli reconnect`;
this does not test profile persistence or automatic guest UI reconnection.
Kindle 4, Basic 2014, Basic 2016, KT6 and both MT8171 Scribes passed USB
route/DNS restoration after Wi-Fi loss. Kobo dhcpcd retains USB DNS through `resolv.conf.tail`;
Forma passed loss/rejoin with the stock DHCP client. ChipIdea/MAX77796 USB
reconnect passed repeated 2, 5 and 20-second cable removals on Oasis 3; MTU3 cable removal/reinsertion passed while
Wi-Fi remained active. MT8171 models a three-second beacon-loss interval and
completes the stock WTBL, station-statistics and channel-status queries so
telemetry cannot block subsequent network commands. A brief interruption
also passed without losing the station connection.

Evidence is in `build/network-audit/2026-09-20-fixes/`, with per-model command,
serial and packet logs. The initial, pre-fix audit is retained separately in
`build/network-audit/2026-09-20/`. MT8110/MT8113 and MT8171 additionally passed DNS
and a 4,983-byte HTTP fetch through Wi-Fi. The temporary generated images and
operational probe helper are under `/tmp/eink-network-fix/`.

The virtual AP is open and fixed to `Kindle-QEMU`; WPA authentication, arbitrary
AP configuration and real RF behavior are not implemented. Deep-suspend radio
recovery and every firmware/profile combination have not been exhaustively
validated. Optional stock hardware telemetry is incomplete. These checks prove
network transport, not Amazon registration, every GUI workflow or physical
panel behavior.
